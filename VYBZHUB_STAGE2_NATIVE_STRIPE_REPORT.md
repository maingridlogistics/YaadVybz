## FAILURE

### Original error file
`hooks/useCustomerTicketing.tsx`

### Original error function
`useNativeTicketCheckout.startCheckout` — Step 2 block

### Exact original failing stage
`initPaymentSheet(...)` — Step 2 of the 4-step native checkout sequence

### Actual Stripe/native error
`initPaymentSheet` returns `{ error: { code: '...', message: '...' } }` when called with `customerId` but **without** the required `customerEphemeralKeySecret`. The Stripe React Native SDK requires both be present or both absent. Passing only `customerId` is an invalid configuration that causes the PaymentSheet to fail initialization before any UI is shown. The user sees: `"Unable to initialize payment. Please try again."`

### Root Cause — CONFIRMED

**`customerId` was passed to `initPaymentSheet` without a matching `customerEphemeralKeySecret`.**

The `create-ticket-payment-intent` Edge Function correctly creates/retrieves a Stripe Customer and returns `customer_id` in the response. `useNativeTicketCheckout.startCheckout` then passed this `customer_id` directly into `initPaymentSheet` as `customerId`.

Per Stripe's PaymentSheet documentation:
> *If you set `customerId`, you **must** also provide `customerEphemeralKeySecret` (a short-lived key that allows the PaymentSheet to access saved payment methods for that customer). Providing `customerId` alone is invalid and causes initialization failure.*

The Edge Function never generated or returned an ephemeral key. The client assumed `customerId` alone was sufficient. It is not.

### Secondary Contributing Factor

Apple Pay was configured on iOS with `applePay: { merchantCountryCode: 'JM' }` unconditionally. The merchant identifier `merchant.com.chambex.vybzhub` in `app.config.js` is explicitly documented as a **placeholder** requiring registration with Apple Developer Portal and Stripe. On a real iOS device, an unregistered merchant identifier causes PaymentSheet to fail even when card payment would otherwise work. This was masked in browser preview (web stub), which is why checkout appeared to work in preview but failed on device.

### Failure Classification

**CASE D** — PaymentIntent creation succeeded on the backend (Stripe customer created, PaymentIntent created, client secret returned), but `initPaymentSheet` failed on the native client due to invalid SDK configuration.

## NATIVE STRIPE

- **Stripe RN version:** `0.74.0` (confirmed in `app.config.js` plugin reference; prior audit confirmed this version)
- **StripeProvider placement:** `<StripeProvider>` wraps the inner `CheckoutScreenInner` component in `app/ticketing/checkout/[eventId].tsx`. This is correct — StripeProvider is present for the entire checkout lifecycle.
- **Provider condition:** `if (useNative && STRIPE_PUBLISHABLE_KEY)` — StripeProvider is only mounted when the key is non-empty AND platform is native. If `EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY` is missing or empty in the EAS environment, `StripeProvider` is **not mounted** and the `useStripe()` hook will return the web stub — which also explains the failure. **MUST VERIFY THIS KEY IS SET IN EAS.**
- **PaymentIntent client secret:** Returned as `payment_intent_client_secret` from Edge Function. Now validated before calling `initPaymentSheet` — rejects if missing or if string does not start with `pi_`.
- **Customer ID:** `customer_id` is returned from Edge Function and stored in `piResult.customer_id` — but is **no longer passed to `initPaymentSheet`**. The PI is still attached to the Stripe customer server-side. Card saving and saved payment methods are not required for ticket checkout.
- **Ephemeral key:** Not generated by backend, not passed to SDK. Correctly omitted alongside `customerId`.
- **returnURL:** `'vybzhub://stripe-return'` — scheme `vybzhub` is configured in `app.config.js` as the Expo URL scheme. This is correct.
- **App scheme:** `vybzhub` — confirmed in `app.config.js` (`urlScheme: "vybzhub"` in Stripe plugin config and `returnURL: 'vybzhub://stripe-return'`)
- **Apple Pay involvement:** YES — was unconditionally enabled on iOS including in test mode and with an unregistered placeholder merchant ID. **FIXED:** Apple Pay is now disabled when `publishableKey.startsWith('pk_test_')` (test mode). In live mode, Apple Pay requires the merchant ID to be registered with both Apple Developer Portal and Stripe Dashboard before it will work without errors. Until registration is complete, consider disabling Apple Pay entirely.

## BACKEND

- **PaymentIntent Edge Function:** `create-ticket-payment-intent/index.ts` — **CORRECT**. Full server-side validation: auth, event, terms, inventory reservation, immutable order/items, integer-only fee arithmetic, Stripe PaymentIntent creation with `automatic_payment_methods`, rollback on any failure.
- **Authentication:** JWT extracted from `Authorization` header, validated via `supabaseAdmin.auth.getUser(token)`. **CORRECT.**
- **Server-side amount:** All pricing computed server-side: `base_subtotal_minor`, `customer_fee_minor` = round(base × 5/100), `customer_total_minor` = base + fee. Client-provided amounts are completely ignored. **CORRECT.**
- **Currency:** Stored as uppercase in DB (`USD`/`JMD`), sent to Stripe as lowercase (`usd`/`jmd`). Both `USD` and `JMD` are supported Stripe currencies. **CORRECT.**
- **PaymentIntent creation:** Uses `automatic_payment_methods: { enabled: true }` — enables cards, Apple Pay, Google Pay, Link etc. where eligible. Order metadata includes `checkout_type: 'ticket'`, `order_id`, `order_number`, `event_id`, `buyer_id`. Webhook uses these for ticket finalization.

- **Double-tap prevention:** `checkoutStatus` state machine prevents re-entry. `isLoading` is `true` during `creating`/`presenting`/`processing` states. The Checkout button in `app/ticketing/checkout/[eventId].tsx` is `disabled={isCheckingOut}`. **CONFIRMED CORRECT.**

### 2. Stripe + Apple Pay (live mode only)

- Register `merchant.com.chambex.vybzhub` (or your actual merchant ID) in Apple Developer Portal → Certificates, Identifiers & Profiles → Merchant IDs
- Add the merchant ID to Stripe Dashboard → Settings → Payment methods → Apple Pay
- If not yet registered, Apple Pay is automatically disabled in test mode (by the fix), and will be disabled on live mode until registration is complete (initPaymentSheet will fail with Apple Pay misconfiguration if enabled before registration)
- **To temporarily disable Apple Pay entirely in live mode too**, change the `applePay` condition to `undefined` until registration is confirmed

### 3. Stripe mode consistency

- Confirm `STRIPE_SECRET_KEY` (Edge Function secret) and `EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY` (client) are from the **same Stripe account and same mode** (both `pk_test_`/`sk_test_` for testing, or both `pk_live_`/`sk_live_` for production)
- A key mismatch (pk_test + sk_live or vice versa) would cause Stripe PaymentIntent creation to succeed but `initPaymentSheet` to reject the client_secret

        → INSERT ticket_orders (pending)
